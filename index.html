substantivo · camada de grounding para agentes de IA

1.Um feature store para o significado de palavras em contexto — resolve o que "cliente", "ativo" ou "ciclo" significam antes de um agente de IA agir, em vez de deixar ele adivinhar.

"Liste os clientes ativos" — no módulo financeiro isso é contrato vigente; no módulo de vendas, é quem comprou nos últimos 90 dias. Um agente sem onimos escolhe uma leitura e erra em silêncio na outra.

01 · o problema

O erro silencioso

Agentes de IA recebem um pedido em linguagem natural e executam sem garantia de que entenderam os termos do domínio do jeito que o sistema espera.

O exemplo que deu origem a este projeto é direto: "liste os clientes" significa coisas diferentes dependendo de onde é pedido. No módulo de vendas, cliente é quem já comprou. No módulo de parcerias, cliente pode ser o revendedor que compra para revender, não para consumir. Um agente que resolve "cliente" sempre do mesmo jeito acerta na maioria dos casos — e erra silenciosamente nos outros. O erro silencioso é o pior tipo de erro, porque ninguém percebe até o dado sair errado num relatório.

Esse problema tem nome fora do mundo de agentes: polissemia de termos de domínio, bem conhecido em NLU empresarial e ferramentas de texto-para-SQL. A solução estabelecida é uma camada semântica — um glossário de negócio entre o pedido e a execução, resolvendo o que cada termo significa antes de deixar o agente agir. O onimos é essa camada, implementada como um feature store de significado: registro versionado, leitura rápida separada do histórico auditável, e um motor que decide quando é seguro resolver sozinho e quando é preciso perguntar.

02 · o conceito

Por que "feature store" e não "glossário"

Um feature store de ML existe pra resolver o training-serving skew: times diferentes calculam a mesma métrica de formas diferentes. A solução é centralizar a definição num registro único, com dono, versão, e dois modos de servir o dado.

O mesmo problema estrutural existe pra significado de palavra. A diferença é que aqui a "feature" não é um número — é uma definição em texto, associada a um escopo (módulo, papel do usuário, tenant) que diz em qual contexto ela vale. O nome vem do sufixo grego -ônimo, o mesmo de sinônimo, hipônimo e homônimo: cada lema pode ter vários onimos, e o sistema decide qual se aplica.

03 · estrutura de dados

OnimoEntry e OnimoRepository

Cada sentido possível de um termo é uma OnimoEntry. O repositório agrupa entradas por termo e mantém um watermark global usado pelo agente pra saber quando o vocabulário mudou.

src/onimos/repository.pypython
@dataclass
class OnimoEntry:
    id: str
    term: str
    definition: str
    scope: dict[str, str]
    excludes: list[str]
    version: int
    valid_from: datetime
    valid_to: datetime | None = None

    def is_current_at(self, as_of: datetime) -> bool:
        return self.valid_from <= as_of and (self.valid_to is None or as_of < self.valid_to)

scope é um dicionário livre de sinais de contexto — {"modulo": "vendas"}, ou vazio pra uma definição genérica. É esse campo que separa este modelo de um dicionário chave-valor plano: em vez de uma definição por termo, existem várias, cada uma marcada com a condição em que se aplica. excludes guarda o que uma definição deliberadamente não cobre. Uma entrada nunca é editada in-place: quando a definição muda, a antiga recebe valid_to e uma nova é criada com version incrementado.

honestidade técnica

O que falta pra ser uma ontologia de verdade

O nome promete ontologia, mas a estrutura hoje é uma lista de entradas por termo, sem relação entre elas. Um modelo completo trataria cada onimo como nó de grafo — é-um / generaliza, exclui como aresta real, mesmo-que pra sinônimos entre times. A implementação atual é o caso de uso mínimo que já resolve o problema original; o grafo é a extensão natural quando o volume justificar.

04 · algoritmo de escrita

Nada é sobrescrito

Escrever uma nova definição nunca apaga a anterior — fecha a versão vigente e abre uma nova. É o que garante correção ponto-no-tempo.

v1 · fechada há 30 dias

"Cliente que comprou nos últimos 90 dias."

v2 · vigente

"Cliente que comprou nos últimos 60 dias."

Consultando a definição vigente hoje, o resultado é v2. Consultando a definição vigente 29 dias atrás, o resultado é v1 — preservada, mesmo depois da atualização. Apagar informação exigiria uma operação separada e deliberada, que o sistema atual não expõe.

06 · algoritmo de busca

Três tentativas até o hash set

Antes de resolver qualquer termo, é preciso achar quais termos do pedido aparecem no vocabulário cadastrado. Medido com 5000 termos sintéticos:

255ms
regex por termo — custo proporcional ao vocabulário
0,01ms
Aho-Corasick — rápido pra ler, caro pra reconstruir
0,008ms
hash set com janela — implementação final

Na leitura, Aho-Corasick e hash set ficam tecnicamente empatados. Na escrita — adicionar 50 termos a um glossário de 5000 — o hash set é cerca de trinta vezes mais rápido (0,005s contra 0,16s), porque add_term é O(1) e não depende do resto do vocabulário. Como um glossário mantido por vários times recebe termo novo com frequência, essa diferença pesa mais no dia a dia.

src/onimos/term_matcher.pypython
def extract(self, text):
    words = _TOKEN_RE.findall(text.lower())
    found = set()
    n = len(words)
    for start in range(n):
        canonical = self._variant_to_term.get(words[start])
        if canonical:
            found.add(canonical)
        if words[start] not in self._first_words:
            continue
        limit = min(self._max_words, n - start)
        for length in range(2, limit + 1):
            candidate = " ".join(words[start:start + length])
            canonical = self._variant_to_term.get(candidate)
            if canonical:
                found.add(canonical)
    return sorted(found)

Ordenar os termos não ajuda; indexar por primeira palavra ajuda. Guardar um conjunto separado (_first_words) com as palavras que iniciam termo composto, e só montar janela de 2+ palavras quando a atual pertence a esse conjunto, é cerca de três vezes mais rápido que testar toda janela incondicionalmente — com o mesmo resultado.

07 · TTLCache

A camada online

Thread-safe, com expiração por tempo e limite de tamanho (LRU quando excede). Só participa de consultas "agora" — consulta ponto-no-tempo vai direto ao repositório, porque é rara e usada principalmente por auditoria.

08 · AuditSink

Toda resolução vira registro

Resolvida ou ambígua, cada resolução gera uma entrada com termo, status, contexto e — quando resolvido — o id e a version exatos da definição escolhida, não só o texto. Interface mínima, trocável por Kafka, Kinesis ou logger estruturado em produção.

09 · o agente

ContextGroundingAgent

Junta as peças anteriores num pipeline único, chamado antes de qualquer agente que execute a tarefa de fato.

src/onimos/grounding_agent.pypython
result = grounding_agent.ground(user_query, context_signals)

if result.needs_clarification:
    return ask_user(result.clarification_questions)

executor_agent.run(prompt=result.grounded_context + "\n\nTarefa: " + user_query)

Se algum termo ficou ambíguo, o pipeline para ali e devolve a pergunta — nenhuma tarefa é executada em cima de uma suposição. Pra processamento em lote, ground_many reaproveita o mesmo matcher e cache já aquecido entre chamadas.

10 · caso de uso real

Mesma pergunta, duas respostas certas

"Calcule o faturamento médio dos clientes ativos no último ciclo."

O matcher reconhece três termos: ativo, ciclo e cliente. "Faturamento médio" não está cadastrado — passa direto, sem gerar contexto nem bloquear.

contexto: módulo financeiro
ativo

Contrato ou assinatura que não está cancelado nem suspenso.

ciclo

Período de fechamento contábil, geralmente mensal.

cliente

Qualquer pessoa ou empresa cadastrada na base, independentemente de ter comprado.

contexto: módulo vendas
ativo

Cliente que fez ao menos uma compra nos últimos 90 dias.

ciclo

Intervalo entre metas de vendas, geralmente trimestral.

cliente

Pessoa ou empresa que já efetuou pelo menos uma compra. (não inclui: revendedores)

Um agente executor sem essa camada, sem saber de qual módulo veio o pedido, muito provavelmente assumiria a leitura mais comum — vendas — mesmo partindo de um contexto financeiro, e calcularia a média em cima da base errada de clientes. 12 · limitações conhecidas

O que ainda não resolve

Persistência

O repositório em memória não sobrevive a um restart nem é compartilhado entre processos. O passo real seguinte pra produção é uma tabela versionada num banco relacional.

Cache distribuído

O cache é local a cada instância do agente. Aceitável com TTL curto; exigiria um Redis compartilhado se a leitura precisar ser idêntica entre instâncias.

Vocabulário novo

A extração de termos depende inteiramente do que já está cadastrado — não é um NER de verdade. Termo novo passa direto, sem bloquear.

Camada ontológica

Relações entre onimos, herança de definição e exclusões como arestas de verdade seguem como extensão conceitual — não implementada.
