01 · the problem

The silent error

AI agents receive a request in natural language and execute it with no guarantee they understood the domain terms the way the system expects.

The example that started this project is straightforward: "list the clients" means different things depending on where it's asked. In the sales module, a client is someone who already bought. In the partnerships module, a client might be the reseller who buys to resell, not to consume. An agent that always resolves "client" the same way gets it right most of the time — and silently gets it wrong the rest of the time. The silent error is the worst kind of error, because nobody notices until the data comes out wrong in some report.

This problem has a name outside the world of agents: domain-term polysemy, well known in enterprise NLU and text-to-SQL tools. The established solution is a semantic layer — a business glossary that sits between the request and execution, resolving what each term means before letting the agent act. onimos is that layer, implemented as a meaning feature store: a versioned registry, fast reads kept separate from an auditable history, and a resolution engine that decides when it's safe to resolve automatically and when it needs to ask.

02 · the concept

Why "feature store" and not "glossary"

An ML feature store exists to solve training-serving skew: different teams calculate the same metric in different ways. The solution is to centralize the definition in a single registry, with an owner, a version, and two ways of serving the data.

The same structural problem exists for word meaning. The difference is that here the "feature" isn't a number — it's a text definition, tied to a scope (module, user role, tenant) that says which context it applies in. The name comes from the Greek suffix -onym, the same one in synonym, hyponym and homonym: each lemma can have several onimos, and the system decides which one applies.

03 · data structure

OnimoEntry and OnimoRepository

Each possible sense of a term is an OnimoEntry. The repository groups entries by term and keeps a global watermark the agent uses to know when the vocabulary has changed.

src/onimos/repository.pypython
@dataclass
class OnimoEntry:
    id: str
    term: str
    definition: str
    scope: dict[str, str]
    excludes: list[str]
    version: int
    valid_from: datetime
    valid_to: datetime | None = None

    def is_current_at(self, as_of: datetime) -> bool:
        return self.valid_from <= as_of and (self.valid_to is None or as_of < self.valid_to)

scope is a free-form dictionary of context signals — {"module": "sales"}, or empty for a generic definition. This is the field that separates this model from a plain key-value dictionary: instead of one definition per term, there are several, each tagged with the condition under which it applies. excludes holds what a definition deliberately does not cover. An entry is never edited in place: when a definition changes, the old one gets a valid_to and a new one is created with version incremented.

technical honesty

What's missing to be a real ontology

The name promises an ontology, but the structure today is a list of entries per term, with no relationship between them. A full model would treat each onimo as a graph node — is-a / generalizes, excludes as a real edge, same-as for synonyms used by different teams. The current implementation is the minimal use case that already solves the original problem; the graph is the natural extension once volume justifies it.

04 · write algorithm

Nothing gets overwritten

Writing a new definition never deletes the previous one — it closes the current version and opens a new one. That's what guarantees point-in-time correctness.

v1 · closed 30 days ago

"Client who bought in the last 90 days."

v2 · current

"Client who bought in the last 60 days."

Querying the current definition today returns v2. Querying the current definition 29 days ago returns v1 — preserved, even after the update. Deleting information would require a separate, deliberate operation that the current system doesn't expose.

05 · scope resolution

Ambiguity is never guessed

Once candidates are found, each entry scores by the number of scope keys that match the current context. A tie or zero score becomes a question, never a guess.

06 · search algorithm

Three attempts to reach the hash set

Before resolving any term, you first need to find which terms in the request appear in the registered vocabulary. Measured with 5000 synthetic terms:

255ms
regex per term — cost proportional to vocabulary size
0.01ms
Aho-Corasick — fast to read, expensive to rebuild
0.008ms
hash set with window — final implementation

On reads, Aho-Corasick and the hash set are technically tied. On writes — adding 50 terms to a glossary of 5000 — the hash set is about thirty times faster (0.005s vs 0.16s), because add_term is O(1) and doesn't depend on the rest of the vocabulary. Since a glossary maintained by several teams gets new terms frequently, that difference matters more day to day.

src/onimos/term_matcher.pypython
def extract(self, text):
    words = _TOKEN_RE.findall(text.lower())
    found = set()
    n = len(words)
    for start in range(n):
        canonical = self._variant_to_term.get(words[start])
        if canonical:
            found.add(canonical)
        if words[start] not in self._first_words:
            continue
        limit = min(self._max_words, n - start)
        for length in range(2, limit + 1):
            candidate = " ".join(words[start:start + length])
            canonical = self._variant_to_term.get(candidate)
            if canonical:
                found.add(canonical)
    return sorted(found)

Sorting the terms doesn't help; indexing by first word does. Keeping a separate set (_first_words) of words that start a compound term, and only building a 2+ word window when the current word belongs to that set, is about three times faster than testing every window unconditionally — with the same result.

07–08 · online store and history

Cache in front, audit trail behind

07 · TTLCache

The online layer

Thread-safe, with time-based expiration and a size limit (LRU eviction when it's exceeded). Only serves "now" queries — a point-in-time query goes straight to the repository, because it's rare and mostly used for auditing.

08 · AuditSink

Every resolution becomes a record

Resolved or ambiguous, every resolution generates an entry with the term, status, context, and — when resolved — the exact id and version of the definition chosen, not just the text. A minimal interface, swappable for Kafka, Kinesis, or a structured logger in production.

09 · the agent

ContextGroundingAgent

Ties the previous pieces together into a single pipeline, called before any agent that actually executes the task.

src/onimos/grounding_agent.pypython
result = grounding_agent.ground(user_query, context_signals)

if result.needs_clarification:
    return ask_user(result.clarification_questions)

executor_agent.run(prompt=result.grounded_context + "\n\nTask: " + user_query)

If any term stayed ambiguous, the pipeline stops right there and returns the question — no task ever runs on top of a guess. For batch processing, ground_many reuses the same matcher and an already-warmed cache across calls.

10 · real use case

Same question, two correct answers

"Calculate the average revenue of active clients in the last cycle."

The matcher recognizes three terms: active, cycle, and client. "Average revenue" isn't registered — it passes through, without generating context or blocking.

context: finance module
active

A contract or subscription that isn't canceled or suspended.

cycle

Accounting close period, usually monthly.

client

Any person or company registered in the database, whether or not they've purchased.

context: sales module
active

A client who has made at least one purchase in the last 90 days.

cycle

Interval between sales targets, usually quarterly.

client

A person or company that has made at least one purchase. (does not include: resellers)

An executor agent without this layer, not knowing which module the request came from, would most likely assume the most common reading — sales — even starting from a finance context, and calculate the average over the wrong client base. 12 · known limitations

What it still doesn't solve

Persistence

The in-memory repository doesn't survive a restart and isn't shared across processes. The real next step for production is a versioned table in a relational database.

Distributed cache

The cache is local to each agent instance. Fine with a short TTL; would need a shared Redis if reads need to be identical across instances.

New vocabulary

Term extraction depends entirely on what's already registered — it's not a real NER. A new term passes through without blocking anything.

Ontological layer

Relationships between onimos, definition inheritance, and exclusions as real edges remain a conceptual extension — not implemented.
